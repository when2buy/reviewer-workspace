### What This PR Does (Plain Language)
This PR adds a crypto benchmark task where an agent must analyze BTCUSDT perpetual funding-rate data, compare behavior across 2022 and 2023 market regimes, fit an Ornstein-Uhlenbeck model, and simulate the return and risk of a basis-carry trade. In plain terms, the agent has to turn raw exchange funding data into a full statistical and risk-analysis package.

Review focus: there are two benchmark-integrity risks here. First, the PR is not cleanly scoped, because it also includes a full unrelated weather-derivatives task. Second, the verifier exposes a large amount of oracle-level numeric information, which weakens contamination resistance and makes the task easier to game by targeting pinned outputs rather than solving the analysis honestly.

### A. Structural Completeness — 3/10
The crypto task itself is substantial and the instruction is detailed. But the PR is structurally not review-ready because it is not scoped to one task.

This PR includes a second complete task, `tasks/cme-hdd-option-pricing/*`, alongside `tasks/crypto-funding-rate-basis-carry/*`. That makes provenance, discussion, scoring, and merge decisions unnecessarily noisy.

Fix: split `cme-hdd-option-pricing` into its own PR.

### B. Task Contract & Determinism — 7/10
The task contract is actually fairly strong on determinism. It explicitly fixes decimal-vs-bps interpretation, annualization periods, ADF settings, the OU plug-in convention, exact OU transition simulation, timestamp formatting, and loss-sign conventions.

That clarity is good. It reduces ambiguity that would otherwise create multiple equally valid implementations.

The tradeoff is that the task is now highly specified, so the verifier should avoid over-sharing the exact final numeric targets.

### C. Reasoning & Benchmark Signal — 7/10
The task does test several real failure modes that matter:
- unit confusion between decimal rates and bps,
- incorrect annualization,
- OU parameterization mistakes,
- wrong sign convention for VaR/CVaR,
- timestamp-cleaning sloppiness.

That is useful benchmark signal. The problem is not the task idea, it is that the visible verifier gives away too much of the answer surface.

### D. Evaluation Criteria & Verifier Quality — 3/10
**[CRITICAL] The PR is not cleanly scoped to a single task**  
Files: `tasks/crypto-funding-rate-basis-carry/*`, `tasks/cme-hdd-option-pricing/*`

This PR adds two different benchmark tasks. That should block merge as a review-unit hygiene issue.

Suggested fix: split the HDD option-pricing task into a separate PR.

**[CRITICAL] The verifier exposes an almost complete oracle surface**  
File: `tasks/crypto-funding-rate-basis-carry/tests/test_outputs.py`

The test file pins a very large fraction of the task's final answers directly or near-directly, including:
- exact observation counts and date endpoints,
- multiple descriptive statistics,
- regime means, positivity rates, and OU kappas,
- full-sample OU parameters and OLS diagnostics,
- Monte Carlo return moments and percentiles,
- output CSV structure and selected endpoint values,
- multiple mirrored intermediates in `solution.json`.

That may still be deterministic, but it weakens contamination resistance and makes the task easier to target by reproducing visible constants rather than solving from first principles.

Suggested fix: reduce direct pinning, move more checks to hidden-reference comparisons or invariant-style validation, and avoid mirroring the entire answer surface across multiple output files.

**[MINOR] The reference solution accepts `cvar_conf` but does not use it independently**  
File: `tasks/crypto-funding-rate-basis-carry/solution/solve.py`

`mc_basis_carry(..., var_conf, cvar_conf)` accepts both thresholds, but the actual tail construction is anchored off the VaR cutoff and does not independently use `cvar_conf`. With current params this is masked because both confidence levels are effectively aligned, but it is still a spec/oracle mismatch.

Suggested fix: either compute CVaR using `cvar_conf` explicitly, or remove the extra parameter if the task intends them to be fixed together.

### Summary
This is a solid task idea with believable medium-difficulty failure modes, but the current PR should not merge in this form. The scope issue alone is blocking because it combines two unrelated tasks in one PR. Even after that split, the verifier still needs work because it exposes too much oracle-level numeric detail.
