### What This PR Does (Plain Language)
This PR adds a crypto benchmark task where an agent must analyze BTCUSDT perpetual funding-rate data, compare behavior across 2022 and 2023 market regimes, fit an Ornstein-Uhlenbeck model, and simulate the return and risk of a basis-carry trade. In plain terms, the agent has to turn raw exchange funding data into a full statistical and risk-analysis package.

Review focus: under the Harbor execution model, visible verifier logic is not treated as a leakage blocker when agents cannot access `/tests` at runtime. The real blockers here are PR scope hygiene and contract / implementation alignment.

### A. Structural Completeness — 3/10
The crypto task itself is substantial and well specified. But the PR is structurally not review-ready because it is not scoped to one task.

This PR includes a second complete task, `tasks/cme-hdd-option-pricing/*`, alongside `tasks/crypto-funding-rate-basis-carry/*`. That makes provenance, discussion, merge decisions, and future debugging noisier than necessary.

Fix: split `cme-hdd-option-pricing` into its own PR.

### B. Task Contract & Determinism — 7/10
The instruction is fairly strong on determinism. It explicitly fixes decimal-vs-bps interpretation, annualization periods, ADF settings, the OU parameterization, exact OU transition simulation, timestamp formatting, and loss-sign convention.

That is good. The remaining contract issue is that `params.json` and the function signature suggest separate `var_confidence` and `cvar_confidence` controls, but the implementation does not appear to use them independently.

### C. Reasoning & Domain Knowledge — 7/10
The task exercises meaningful crypto-specific reasoning failures: unit confusion, annualization mistakes, OU fitting details, sign-convention errors, and timestamp cleaning. That is legitimate benchmark signal for a medium crypto task.

### D. Evaluation Criteria & Grading Reliability — 7/10
Under Harbor, visible tests are not a blocker by themselves because agents do not see them at runtime. On that standard, the grading setup is not the main issue here.

The more important grading-related concern is contract alignment: if a parameter exists and is presented as configurable, the reference implementation should either respect it or remove it from the contract.

### Findings

**[CRITICAL] The PR is not cleanly scoped to a single task**  
Files: `tasks/crypto-funding-rate-basis-carry/*`, `tasks/cme-hdd-option-pricing/*`

This PR adds two different benchmark tasks. That should block merge as a review-unit hygiene issue.

Suggested fix: split the HDD option-pricing task into a separate PR.

**[MINOR] `cvar_confidence` is not used as an independent parameter in the reference implementation**  
File: `tasks/crypto-funding-rate-basis-carry/solution/solve.py`

`mc_basis_carry(..., var_conf, cvar_conf)` accepts both thresholds, but the CVaR calculation is effectively anchored off the VaR cutoff rather than using `cvar_conf` independently. With the current task settings this may be masked, but it is still a contract / implementation mismatch.

Suggested fix: either compute CVaR using `cvar_confidence` explicitly, or remove the extra parameter if the task intends the two confidence levels to be fixed together.

### Summary
This is a solid crypto task idea, and under Harbor's runtime model I am not treating visible test logic as a blocker. The real issue is simpler and harder: this PR bundles two unrelated tasks, which should block merge on scope hygiene alone. There is also a smaller contract mismatch around `cvar_confidence` in the reference implementation.
