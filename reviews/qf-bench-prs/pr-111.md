### What This PR Does (Plain Language)
This PR adds a benchmark task where an agent must clean a return dataset and then compute historical Value at Risk, a standard risk measure based on the worst losses in the sample. In plain terms, the agent has to turn a messy market dataset into a clean one, explain what was removed, and report the portfolio loss threshold implied by the cleaned history.

Review focus: the main benchmark risk here is not raw financial math difficulty, it is contract determinism. If multiple reasonable cleaning orders produce the same final dataset and the same VaR outputs, the task should not secretly require one hidden intermediate path. The second risk is verifier integrity: if the PR description says the verifier recomputes expected values, but the test actually just pins constants, reviewers and contributors are being told the wrong thing about how the task is judged.

### A. Structural Completeness — 8/10
The task itself is coherent: clean data, produce a cleaning report, and compute historical VaR outputs. The workflow is reproducible in broad shape, and the existing draft review does not indicate any missing core task files.

The main weakness here is not missing structure but mismatched claims about how the task is judged. That pushes this PR below review-ready quality even though the task skeleton is otherwise reasonable.

### B. Task Contract & Determinism — 5/10
The largest issue is that the task appears to require one hidden canonical cleaning order without actually specifying that order in the public contract. According to the existing review notes, the instruction tells the agent to determine the correct order of operations and says tests will verify consistency with a canonical ordering, but that ordering is not disclosed.

That is a determinism problem. If multiple reasonable cleaning orders yield:
- the same final cleaned dataset,
- the same `n_observations_clean`,
- the same VaR outputs,
- and the same worst-loss day,

then the benchmark should not fail an agent purely because its intermediate removal counts differ from an undisclosed reference path.

Fix: either specify the cleaning order explicitly in `instruction.md`, or redesign the tests so they validate final cleaned outputs and material invariants instead of exact intermediate attribution.

### C. Reasoning & Benchmark Signal — 6/10
As an easy task, the financial workflow is plausible and useful. Cleaning a returns panel and then producing a historical VaR estimate is realistic enough to be benchmark-worthy.

The weak point is that the current extra reporting field `per_asset_observations` does not appear to add much reasoning signal if the task already mandates listwise deletion. In that setup, every final per-asset count should collapse to the same cleaned-row count, so this section risks becoming output bulk without meaningful discrimination.

Fix: either remove that field, or replace it with something that reveals whether the agent actually understood the cleaning logic rather than just mirrored a mechanical count.

### D. Evaluation Criteria & Verifier Quality — 4/10
Two verifier issues block confidence in the current form.

**[MAJOR] Hidden canonical path enforced through exact count checks**
The verifier appears to check exact intermediate removal counts, which over-constrains the task relative to the public instruction. This is not just a wording issue, it can cause valid implementations to fail for non-substantive reasons.

**[MAJOR] PR description misstates how the verifier works**
The PR notes reportedly say the verifier recomputes canonical values internally, but the test file uses a hard-coded `EXPECTED` dictionary for key outputs and counts. That mismatch matters because it overstates robustness and can mislead reviewers about contamination resistance.

**[MAJOR] `tests/test.sh` uses the brittle `$?` reward pattern**
If the verifier shell uses `set -euo pipefail` and then checks `$?` only after the main `pytest` invocation, the failure branch may never execute on test failure. That means reward emission on failure is not reliable.

Fixes:
- align the public PR description with the actual verifier design,
- avoid checking undisclosed intermediate counts unless the contract explicitly requires them,
- and rewrite the shell wrapper using `if ...; then ... else ... fi` so failures reliably write reward `0`.

### Summary
This is a reasonable easy-difficulty task idea, but the current benchmark contract is not deterministic enough for review approval. The biggest blocker is the hidden canonical cleaning-order requirement: if the instruction does not disclose that path, the verifier should not enforce it. The second blocker is verifier hygiene, both in the inaccurate PR description and in the fragile reward-writing shell pattern.
