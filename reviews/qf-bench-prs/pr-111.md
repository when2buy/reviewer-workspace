## Summary
PR #111 is a clean single-task addition, and the core task is understandable and reproducible. The data-cleaning + historical VaR workflow is realistic enough for an easy benchmark, and the oracle solution matches the pinned outputs. However, the benchmark currently over-specifies one hidden cleaning-order convention through exact count checks, even though many equally valid cleaning orders produce the same final cleaned dataset and identical VaR outputs. The verifier also uses the brittle reward-writing pattern, and the PR description incorrectly claims the verifier recomputes canonical values internally when it actually pins constants in the test file.

## Findings

### [MAJOR] The task hides a canonical cleaning-order requirement that is not actually specified
`instruction.md` says the agent is responsible for determining the “correct order of operations” and that tests will verify consistency with a canonical ordering, but that ordering is never disclosed.

This matters because multiple reasonable orderings produce:
- the same final cleaned dataset,
- the same `n_observations_clean`,
- the same VaR values,
- the same worst day,

but different intermediate removal counts in `cleaning_report`.

### [MAJOR] The verifier pins oracle constants instead of recomputing from inputs
The PR notes say “The verifier recomputes canonical values internally,” but `tests/test_outputs.py` uses a hard-coded `EXPECTED` dict for all key outputs and counts.

### [MAJOR] `tests/test.sh` still uses the fragile `$?` pattern
The verifier script still uses the brittle `$?` pattern after the main `uvx ... pytest ...` invocation.

### [MINOR] `per_asset_observations` is not adding much signal
Because the instruction mandates listwise deletion, every final per-asset count must equal `n_rows_after_cleaning`. So this section is effectively redundant.

## What should change
1. Make the cleaning-order requirement explicit, or relax the tests so they validate final cleaned outputs rather than exact intermediate count attribution.
2. Fix the PR description to match reality: the verifier currently checks against pinned expected values, not recomputed canonical values.
3. Rewrite `tests/test.sh` to avoid the fragile `$?` reward pattern.
4. Optionally simplify or strengthen `per_asset_observations`.

## Verdict
**REQUEST CHANGES**
