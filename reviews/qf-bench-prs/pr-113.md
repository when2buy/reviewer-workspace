## Summary
This task idea is reasonable, but the benchmark quality is weaker than the PR claims. The strongest issues are overstated difficulty, weak model discrimination, low-quality failure evidence, and a brittle verifier shell pattern.

## Scores
- Benchmark integrity / anti-cheating: **3/5**
- Difficulty calibration: **2/5**
- Model discrimination: **2/5**
- Instruction / contract clarity: **4/5**
- Verifier robustness: **2/5**
- Data realism / determinism: **4/5**

## Findings

### [MAJOR] Difficulty appears overstated
The PR labels this task as `hard`, but the provided evidence does not support that calibration. Oracle, Claude Code, and Codex all achieve reward `1.0`, and Codex reportedly completes the task in about 4.5 minutes. This looks closer to a medium task, or even easy-for-frontier-models, rather than a genuinely hard benchmark item.

### [MAJOR] The failure evidence is not very informative
The documented Finance-Zero failure is mainly a schema-assumption crash: it guessed the wrong input schema, produced no outputs, and failed trivially. That shows the task is not solvable by blind schema guessing, but it does not convincingly demonstrate that the underlying ledger / reconciliation logic is difficult.

### [MAJOR] The task currently has weak model discrimination
The current evidence suggests the task mainly separates agents that read the contract carefully from agents that crash early. That is useful to some extent, but it is not the same as demonstrating robust reasoning difficulty.

### [MAJOR] `tests/test.sh` has a brittle failure path
Because the script uses `set -euo pipefail`, a failing `pytest` run can exit immediately before the later `$?` check can write `0` to `/logs/verifier/reward.txt`. Please wrap the pytest call in `if ...; then ... else ... fi`.

### [MINOR] The visible verifier contains a full canonical recomputation
Under Harbor’s execution model this is not a runtime `/tests` leak, since `/tests` is uploaded only after the agent finishes. But from a benchmark-hygiene perspective, exposing the full canonical recomputation in a visible test file still weakens contamination resistance.

## What should change
1. Either increase task difficulty / improve frontier-model failure rate, or downgrade the difficulty label from `hard`.
2. Provide stronger failure evidence showing capable models failing on the actual accounting/reconciliation logic, not just on schema assumptions.
3. Fix the verifier reward-emission path so failures reliably produce reward `0`.
4. Optionally reduce visible oracle exposure in the verifier.

## Verdict
**REQUEST CHANGES**
