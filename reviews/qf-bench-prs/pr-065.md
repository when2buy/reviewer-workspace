# PR #65 — treasury-bond-risk-analytics

- URL: https://github.com/QF-Bench/QuantitativeFinance-Bench/pull/65
- Status: draft
- Preliminary verdict: **REQUEST CHANGES**

## Summary
PR #65 adds a solid fixed-income task with realistic bond analytics and good surface difficulty, but the task contract and verifier are not fully aligned yet. The biggest problems are output-schema mismatches between `instruction.md`, `solution/solve.sh`, and `tests/test_outputs.py`, plus some required outputs that are never actually validated.

## Scores
- Task contract / instruction: **2/5**
- Verifier robustness: **3/5**
- Difficulty calibration: **4/5**
- Model discrimination: **4/5**
- Review hygiene / PR cleanliness: **4/5**
- Data realism / determinism: **4/5**

## Findings

### [MAJOR] `instruction.md` and the verifier disagree on the required `solution.json` keys
The instruction says `solution.json` should contain:
- `BOND_C_last_coupon_date`
- `BOND_C_accrued_days`
- `BOND_D_last_coupon_date`
- `BOND_F_dirty_price`

But the tests actually require:
- `91282CHT5_last_coupon_date`
- `91282CHT5_accrued_days`
- `91282CKB1_last_coupon_date`

And the solution writes:
- `91282CHT5_last_coupon_date`
- `91282CHT5_accrued_days`
- `91282CKB1_last_coupon_date`
- `912810TN8_dirty_price`

So the published contract, the verifier, and the oracle do not match.

### [MAJOR] Some outputs required by the task are never validated
`instruction.md` requires per-bond `mac_duration` and requires `cashflows.csv` with specific columns and semantics. But the tests only check that `cashflows.csv` exists, and they never validate `mac_duration` at all.

### [MAJOR] The scenario P&L documentation is inconsistent
`params.json` sets `"shift_bps": 100`, and the expected `scenario_pnl` is clearly consistent with a 100 bp shock. But `test_scenario_pnl()` says “P&L under +50bp parallel shift...”.

### [MINOR] The instructions over-specify solver method without verifier support
The task explicitly requires Newton-Raphson for YTM and z-spread, but the oracle solution uses a bisection + Newton hybrid. I do not think the benchmark should force a particular numerical method unless that is essential.

### [MINOR] The PR body’s difficulty label is inconsistent with `task.toml`
The PR body calls this “hard difficulty”, while `task.toml` says `difficulty = "medium"`.

## What should change
1. Make `instruction.md`, `tests/test_outputs.py`, and `solution/solve.sh` agree exactly on the `solution.json` intermediate keys.
2. Add verifier checks for all required outputs, especially `mac_duration` and `cashflows.csv` semantics.
3. Fix the scenario P&L test docstring to match the actual `shift_bps` input.
4. Either remove the explicit Newton-Raphson requirement from the instructions, or enforce that requirement more meaningfully.
5. Make the difficulty label consistent between PR metadata and `task.toml`.

## Verdict
**REQUEST CHANGES**
